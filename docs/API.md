# carry os API

## Authentication (development/test only)

Authentication is disabled by default (`AUTH_ENABLED=false`). After the
frontend has a supported NEAR Auth identity JWT handoff and the matching
issuer, audience, and JWKS URL are confirmed, development/test can enable the
backend session exchange. The API does not accept a NEAR account ID or email as
proof of identity.

### `POST /api/auth/near/verify`

Send `Authorization: Bearer <NEAR Auth JWT>`. The API validates the JWT
signature and its configured issuer, audience, subject, and expiry, then
sets the opaque `carry_session` HttpOnly cookie. The JSON response includes
`authenticated`, an opaque Carry user ID, a session-bound `csrfToken`, and the
absolute `expiresAt`. The identity token is never stored.

The browser must send credentials and the allowed `Origin`. For state-changing
routes protected by `AuthSessionGuard`, send the returned CSRF value in
`X-CSRF-Token`; the guard enforces it for non-safe HTTP methods.
Keep it in memory; do not put it in local storage. The session cookie is
HttpOnly, scoped to `/api` so it reaches protected API routes, and SameSite=Lax.
The CSRF token is deterministically derived with a separate server-side HMAC
secret and only its SHA-256 hash is stored with the session. `GET /api/auth/session`
re-derives the token and verifies it against the stored hash after a page reload.

### `GET /api/auth/session`

Requires the session cookie. Returns the Carry user ID, a CSRF token, and the
absolute expiry. Activity refreshes the 30-minute idle timer, but not the
8-hour absolute expiry.

### `POST /api/auth/logout`

Requires the session cookie, allowed `Origin`, and `X-CSRF-Token`. Revokes the
session and clears the cookie.

### Current limits

User identities and sessions are stored in PostgreSQL through Prisma. The
session row contains only hashes for the opaque session and CSRF tokens.
`DATABASE_URL` must be configured when enabling authentication. FastAuth
establishes only the Carry session; it does not prove wallet ownership or
authorize blockchain transactions.

> **Status:** authentication and wallet-linking routes are enabled only when
> `AUTH_ENABLED=true`. Wallet proof is NEP-413 and is separate from session
> authentication. A read-only NEAR testnet demo NFT endpoint is also available.

## 2. Implemented endpoints

### `GET /api/health`

Liveness check. It confirms that the API process is running. It does **not**
check the database, blockchain connectivity, provider health, or custody state.

**Authentication:** none

**Response: `200 OK`**

```json
{
  "status": "ok",
  "service": "carry-os-api",
  "version": "0.1.0",
  "timestamp": "2026-11-06T12:00:00.000Z"
}
```

The response is validated against `healthResponseSchema` in
`packages/shared/src/health.ts`.

### Authentication endpoints

The opt-in development/test endpoints are documented at the top of this file:
`POST /api/auth/near/verify`, `GET /api/auth/session`, and
`POST /api/auth/logout`. They return 503 while `AUTH_ENABLED=false` and are
not production-ready.

### `POST /api/wallets/near/challenge`

Requires the Carry session cookie and `X-CSRF-Token`. Body:

```json
{ "address": "alice.testnet" }
```

The API binds the challenge to the authenticated Carry user, the normalized
NEAR address, the server-selected `WEB_ORIGIN` (first configured origin),
network, purpose, nonce and five-minute expiry. The response includes the
stored message, nonce, recipient and challenge ID needed for NEP-413 signing.
The client cannot set the challenge's Carry user or signing recipient.

### `POST /api/wallets/near/link`

Requires the Carry session cookie and `X-CSRF-Token`. Body:

```json
{
  "challengeId": "8056e8a4-7ec0-47dd-bafc-558b1a9b2781",
  "signature": "<NEP-413 signature>",
  "publicKey": "ed25519:<wallet public key>"
}
```

The API consumes the challenge atomically before signature verification,
verifies the signature and account access key through NEAR RPC, then requires
the challenge's Carry user to match the current session. Failed verification
also consumes the challenge. A unique database constraint prevents a wallet
from being silently linked to another account.

Challenge rows are stored in PostgreSQL. With `AUTH_ENABLED=true`, the API
selects the Prisma-backed challenge and wallet stores; there is no production
fallback to memory. Apply the new Prisma migration before enabling these
routes. When auth is disabled, wallet-linking routes are not registered.

### `GET /api/near/nfts?owner_id=<near-account>`

Reads the configured demo NEP-171 collection and Carry vault using final NEAR
testnet RPC view calls. The API returns wallet-owned tokens plus tokens whose
on-chain depositor or beneficiary is the requested account. It does not persist
NFT ownership, sign transactions, or accept write operations.

**Authentication:** none; this is a public read-only view.

**Response fields:** `collectionId`, `tokenId`, `title`, `media`, `ownerId`,
`depositorId`, `beneficiaryId`, `secured`, and `pendingWithdrawal`.

The endpoint enumerates at most 100 tokens in the configured demonstration
collection and limits per-request custody reads to eight concurrent RPC calls.
Ownership and custody reads use one finalized block height per response. The
response's `secured` value is true only when both the custody record exists and
the NFT owner is the configured vault; `custodyStatus` reports `not_secured`,
`secured`, `withdrawal_pending`, or `inconsistent`. Set
`NEAR_TESTNET_RPC_URL`, `NEAR_VAULT_ACCOUNT_ID`, and
`NEAR_DEMO_NFT_ACCOUNT_ID`. The blockchain contracts remain the source of
custody truth. The API applies a global per-IP in-process rate limit,
configured through `RATE_LIMIT_LIMIT` and `RATE_LIMIT_TTL_SECONDS`. The limiter
is local to one API process; multi-instance deployments also need a shared
gateway limit.

## 4. Planned API domains

The following areas are expected but have **no agreed endpoints or schemas**:

| Domain | Owner | Status |
| --- | --- | --- |
| NEAR authentication | Backend | Development/test JWT exchange implemented; token handoff TBD |
| Sessions and protected access | Backend | PostgreSQL-backed sessions implemented; protected product routes TBD |
| Wallet connection and ownership proof | Frontend/backend | NEAR Wallet Selector; API wallet linking uses session-bound NEP-413 proof |
| NFT discovery | Backend | Read-only demo collection and vault view calls implemented |
| Custody deposit coordination | Frontend/contracts | Wallet-signed testnet call wiring present; deployment and live verification pending |
| Beneficiary changes | Frontend/contracts | Original-depositor wallet call wiring present; live verification pending |
| Withdrawals | Frontend/contracts | Current-beneficiary wallet call wiring present; live verification pending |
| Transaction monitoring | Backend | Not implemented; contract TBD |

Frontend integration is owned by the frontend developer; shared contracts are a
shared responsibility. Do not invent endpoint paths, payloads, or status codes
before approval.

## 5. CORS

The API allows browser origins configured through `WEB_ORIGIN`, a
comma-separated list. The default is `http://localhost:3000`.

## 6. Error handling

A consistent error format, correlation IDs, retry semantics, and rate-limit
responses are **TBD**. Errors must not expose secrets, stack traces, or sensitive

## 7. Security

Authentication is disabled by default. The opt-in session exchange and wallet
link endpoints require configured PostgreSQL storage; FastAuth sessions never
substitute for a wallet signature. The rate limiter is process-local. See
[SECURITY.md](SECURITY.md) for remaining production controls.
